# metabolomics-raw-data-retrieval-from-repository

## Summary

Retrieves raw LC-MS/SWATH-DIA mzML spectra and the associated MS1 feature table from a public repository such as Metabolomics Workbench, using a study accession (e.g., ST002796) as the entry point, so that downstream MetaboAnalystR 4.0 deconvolution and identification can be reproduced.

## When to use

Use when a metabolomics analysis must start from publicly deposited raw spectra — e.g., reproducing a SWATH-DIA benchmark that requires the raw mzML files of a Metabolomics Workbench study plus its MS1 feature table.

## When NOT to use

- A processed MS1 feature/peak table is already in hand and no raw SWATH-DIA MS2 spectra are needed
- The target dataset is stored only as supplementary tables or vendor-format files without raw mzML spectra, so DIA deconvolution cannot be performed
- The analysis only requires reference spectra libraries (HMDB, MoNA, MassBank, GNPS, LipidBlast, MINEs) rather than study raw data

## Inputs

- Metabolomics Workbench study accession (e.g., ST002796, blood exposomics dataset)
- List of sample/replicate identifiers to map mzML files to study conditions

## Outputs

- Raw mzML files containing SWATH-DIA MS1/MS2 spectra for the whole-blood samples
- MS1 feature table generated by MetaboAnalystR auto-optimized peak picking, used as the target feature list for deconvolution

## How to apply

Identify the study accession on Metabolomics Workbench (here ST002796, a whole-blood exposomics dataset) and download the raw mzML SWATH-DIA spectra files it provides. Alongside the raw spectra, obtain or regenerate the MS1 feature table produced by MetaboAnalystR's auto-optimized peak picking, since this feature list is what feeds PerformDIADeconvolution as the target list. Verify that each mzML file contains both MS1 and SWATH-window MS2 scans so that DIA deconvolution is possible. Keep file-to-sample mapping (replicates) intact, because the downstream PerformSpectrumConsenus step merges replicate deconvolved spectra using a 50% fragment-frequency threshold. The rationale is reproducibility: the published benchmark (>1000 level 2a compounds for DIA, >500 for DDA) is defined against exactly these raw inputs, not against preprocessed peak tables.

## Related tools

- **MetaboAnalystR 4.0** (R package installed from GitHub whose auto-optimized peak picking generates the MS1 feature table that accompanies the retrieved raw mzML spectra as the deconvolution target list) — https://github.com/xia-lab/MetaboAnalystR
- **R** (Open-source environment in which MetaboAnalystR is installed (R > 3.6.1 recommended per README) and in which the retrieved spectra are loaded for processing)
- **Metabolomics Workbench** (Public repository hosting the raw mzML SWATH-DIA spectra under accession ST002796 for the blood exposomics dataset)

## Evaluation signals

- Every downloaded mzML file parses as valid mzML and contains SWATH-window MS2 scans plus MS1 survey scans
- The accession (ST002796) resolves on Metabolomics Workbench and the downloaded file set matches the study's declared sample count, including replicates
- The MS1 feature table regenerated via MetaboAnalystR auto-optimized peak picking is consistent with the target feature list expected by PerformDIADeconvolution
- Downstream sanity check: the full pipeline on these inputs yields >1000 level 2a compounds for SWATH-DIA and >500 for DDA (~5% more than non-deconvoluted processing), matching the reported benchmark
- Replicate structure is preserved so PerformSpectrumConsenus can merge deconvolved spectra across replicates at the 50% fragment-frequency threshold

## Limitations

- Raw-data retrieval depends on the repository (Metabolomics Workbench) hosting the study; if only processed files or no mzML are deposited, the SWATH-DIA deconvolution workflow cannot be reproduced
- The downstream reference spectra libraries are 'compiled from various instruments and experimental conditions, resulting in potentially varying qualities', which limits identification confidence regardless of raw-data quality
- No version of the R environment was pinned in the discussion ('within an open-source R environment'), so retrieved-data reproducibility depends on matching package versions separately
