# peak-picking-parameter-optimization

## Summary

Estimate dataset-specific peak-picking parameters for untargeted metabolomics data processing in a single statistical-inference step with AutoTuner (R/BioConductor), instead of iteratively sweeping parameter combinations with tools like IPO. AutoTuner returns seven continuous centWave parameters plus a key XCMS Group parameter directly from raw mass-spectrometry data.

## When to use

Use when raw untargeted metabolomics MS files (mzML, mzXML, CDF) must be peak-picked with centWave in XCMS or MZmine2, but no universal parameter set applies and manual/iterative tuning (e.g. IPO on HPC) is too slow or noisy.

## When NOT to use

- Input is already a processed feature table — parameter optimization must occur on raw data prior to analysis to avoid noise inflation
- Only one or two samples are available — AutoTuner requires at least 3 samples of raw data for estimation
- The Group difference parameter must be estimated automatically — it requires a non-automatable cross-sample comparison during TIC peak detection

## Inputs

- Raw untargeted metabolomics mass-spectrometry sample files converted to .mzML, .mzXML, or .CDF (at least 3 samples; 9 recommended for CV <= 0.1)
- Sample metadata spreadsheet with at least two columns: one matching raw data sample names, one describing experimental factors
- R (version >= 3.6) environment

## Outputs

- Dataset-specific estimates of seven continuous centWave peak-picking parameters plus the XCMS Group parameter
- Downstream processed feature table generated by XCMS centWave peak detection, grouping, and retention-time correction using the estimated parameters

## How to apply

Split the raw files by ionization mode and run AutoTuner on the raw data — it requires at least 3 samples converted to open formats (.mzML, .mzXML, or .CDF) plus a spreadsheet mapping sample names to experimental factors. The first portion of AutoTuner performs a sliding window analysis over the TICs (requires user input), then statistical inference on the raw data estimates the seven continuous centWave parameters (used by both XCMS and MZmine2) plus a key XCMS grouping parameter, in a single step rather than many iterations. The non-automatable Group difference parameter is estimated through a manual cross-sample comparison during the TIC peak detection step, and mzDiff is the one continuous parameter not optimized — select it via a sensitivity analysis showing distinct values have minimal effect on the returned feature table. Use 9 samples (or 9–12 across culture and community datasets) so that estimates reach coefficient of variation <= 0.1, as validated by the paper's Monte Carlo experiment. Feed the resulting parameter set into XCMS centWave peak detection, grouping, and retention-time correction; expect ~100–1000X speedup over iterative approaches, going from days to minutes.

## Evaluation signals

- Monte Carlo check: compute the coefficient of variation across replicate random subsample draws — CV values should drop below 0.1 for most parameters once 9 samples are used
- Downstream comparison: run XCMS with AutoTuner-derived vs IPO-derived parameters and count unique/shared features (paper reports AutoTuner 203/540 unique vs IPO 2606/3420 unique, 1022/904 shared on MTBLS157 positive mode)
- Runtime check: parameter estimation should complete in minutes rather than the days required by iterative optimization (~100-1000X speed improvement)
- Coverage check: exactly seven continuous centWave parameters are returned, with mzDiff explicitly excluded and handled by sensitivity analysis instead
- Sanity check that the Group difference parameter was estimated by manual cross-sample comparison and was not included in automated robustness testing

## Limitations

- The Group difference parameter cannot be checked for robustness because it is estimated through a non-automatable cross-sample comparison
- mzDiff is the one continuous parameter not optimized by AutoTuner; only a sensitivity analysis was performed to show minimal effect on the returned feature table
- The sliding window analysis requires user input during the first portion of AutoTuner
- AutoTuner is not parallelized; parallelization to reduce computation time is a possible future improvement
- The divide-and-conquer speed advantage comes at a loss of comparing EIC peaks across samples to estimate retention time correction algorithms; requires R >= 3.6
