# lcms-peak-table-automated-transfer

## Summary

Automates handoff of MS-DIAL-generated peak tables (in .msdial/.tsv form) to MS-FLO inside the Nextflow4MS-DIAL workflow, eliminating manual copying of intermediate feature tables so that downstream duplicate/adduct/isotope flagging, peak alignment, and contaminant ion removal run unattended.

## When to use

Use when running the Nextflow4MS-DIAL pipeline on .mzML LC-HRMS input and you need MS-DIAL's peak table to flow into MS-FLO automatically without manual file copying or manual re-parameterization between the two tools.

## When NOT to use

- When the input is already a finished, manually curated feature table — this skill's purpose is automated intermediate handoff between MS-DIAL and MS-FLO, not post-hoc table refinement.
- When working outside the Nextflow4MS-DIAL framework (e.g., calling MS-FLO standalone from a separate script) — no containerized, workflow-managed transfer occurs, undermining the reproducibility this skill provides.
- When the raw data are not .mzML or .abf LC-HRMS files, since the workflow only accepts those formats and the handoff depends on MS-DIAL's peak-table output from them.

## Inputs

- MS-DIAL peak table (output .msdial/.tsv file produced from mzML input)
- msdial_params.txt configuration file (in data/ folder)
- msflo_params.ini configuration file (in data/ folder)
- ms1_lib.txt and ms2_lib.msp metabolite library files (optional, in data/ folder)

## Outputs

- MS-FLO-processed peak table with duplicate/adduct/isotope flags, aligned peaks, and contaminant ions removed (25,414 peaks from 25,447 input peaks on MTBLS733)
- execution_report.html summarizing runtime and resource usage
- logs/execution.log recording successful completion of the MS-DIAL-to-MS-FLO transfer

## How to apply

Place mzML files in data/raw_data/ along with msdial_params.txt, msflo_params.ini, ms1_lib.txt, and ms2_lib.msp in the data/ folder (example configs in functional_test/sample_data/), then launch the pipeline via `nextflow run main.nf -profile docker`. Nextflow orchestrates the transfer: after MS-DIAL (version 4.48 in the containerized build) writes its peak table (25,447 peaks on the MTBLS733 test set, file extensions converted from .msdial to .tsv so spreadsheets can open them), the workflow automatically hands the table to MS-FLO with no manual copying or intervention. MS-FLO then enhances data quality through duplicate peak flagging, adduct and isotope flagging, peak alignment, and contaminant ion removal, yielding a refined peak table of 25,414 peaks. The rationale is to minimize human errors from manual data handling and to preserve computational reproducibility via Docker/Singularity containerization on any Unix-like system.

## Evaluation signals

- Confirm no manual file copying occurred between MS-DIAL and MS-FLO by checking logs/execution.log for automatic process chaining.
- Validate that the MS-FLO output is a valid peak table with 25,414 peaks (versus 25,447 from MS-DIAL) on the MTBLS733 test dataset.
- Check that execution_report.html and execution_timeline.html record successful completion of both the MS-DIAL and MS-FLO processes.
- Verify that the output files retain .tsv extensions (converted from .msdial) so they can be opened in spreadsheet software such as Microsoft Excel.
- Run the workflow five times and confirm identical results, matching the article's demonstrated consistent reproducibility.

## Limitations

- MS-FLO must be downloaded from the Internet rather than bundled with the workflow, which can complicate setup.
- The workflow has been tested only on macOS (Intel-based) and Linux (HiPerGator/Red Hat Enterprise Linux 8.8); not yet tested on Apple silicon (M-series) systems.
- Only 10-sample test data and few LC-MS datasets processed with both MS-DIAL and MS-FLO under transparent parameter settings, limiting broad reproduction of the steps.
- The workflow is command-line only; no graphical user interface exists for users with limited computational experience.
- Software updates (e.g., MS-DIAL) are monitored manually, with no efficient maintenance plan for the workflow and container.
