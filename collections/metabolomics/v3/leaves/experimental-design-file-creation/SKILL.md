# experimental-design-file-creation

## Summary

Create the Optimus experimental-design CSV template via the 'Generate template of experimental design' KNIME node, then annotate each LC-MS run with its LC-run type (labelling blank runs as BLANK) and coordinates. This metadata file drives downstream blank filtering, normalization and 'ili spatial mapping.

## When to use

Use when preparing an Optimus (KNIME) LC-MS untargeted metabolomics workflow: you have mzXML sample runs (plus blanks) and need the experimental-design CSV that assigns LC-run type and spatial coordinates before feature filtering and quantification.

## When NOT to use

- A completed experimental-design CSV with correct LC-run type labels already exists for the run set — regenerate only if runs were added or renamed.
- You are downstream of design creation, e.g. running 'Detect LC-MS features', 'Align and quantify features', or 'Filter features' — those consume the design file rather than produce it.
- The task is molecular annotation or normalization of an existing feature table; the design file concerns run-level metadata, not feature-level annotation.

## Inputs

- mzXML LC-MS sample runs (with blank runs, e.g. in a samples/blanks subdirectory as in the apple_samples.zip demo archive)
- stub.txt placeholder input for nodes without a real input file
- coords.csv sample coordinate table (for spatial mapping)

## Outputs

- experimental-design CSV template (generated by the 'Generate template of experimental design' node) with LC-run type column (BLANK/sample) and sample coordinates

## How to apply

After loading the mzXML runs into Optimus's 'Read LC-MS runs' node (internally converted to centroided mzML), execute the 'Generate template of experimental design' node, which emits a design CSV with one row per run. Use stub.txt as the input for nodes that have no real input file. Manually fill in the design table: set the LC-run type column, marking blank/control runs as BLANK, and attach per-sample coordinates (e.g. coords.csv) so features can later be mapped in 2D/3D with the 'ili app. The BLANK labels are essential because the subsequent optional 'Filter features' node excludes features caused by background signals present in BLANK-labelled runs; incorrect or missing labels leave background features in the final features_quantification_matrix.csv.

## Related tools

- **Optimus** (KNIME workflow whose 'Generate template of experimental design' node creates the experimental-design CSV; includes the 'Read LC-MS runs', 'Filter features' and 'Save results' nodes) — https://github.com/MolecularCartography/Optimus
- **KNIME** (Workflow management platform in which the Optimus workflow (Optimus v1.0.0.knwf) is opened and the design-template node is executed) — https://www.knime.org

## Evaluation signals

- The 'Generate template of experimental design' node executes without error and writes a design CSV containing one row per mzXML run loaded into 'Read LC-MS runs'.
- Every blank run is labelled BLANK in the LC-run type column of the design CSV, since the 'Filter features' node removes features present in BLANK-labelled runs.
- The subsequent Save results step produces features_quantification_matrix.csv whose columns follow the format 'mz_value RT charge (ID: numeric_identifier)'.
- The workflow completes without raising the ValueError 'Input list of LC-MS features is empty' listed in the Optimus troubleshooting table.

## Limitations

- Labelling blank runs as BLANK is a manual step in the generated CSV and must be done correctly; mislabelled blanks leak background features into the quantification matrix.
- Optimus temporary files are not deleted automatically (to allow re-execution), so repeated design/workflow iterations consume extra disk space.
- Experimental design generation presupposes the KNIME + Python 2.7 + pyopenms installation stack; only 64-bit MS Windows, Linux and macOS are supported.
