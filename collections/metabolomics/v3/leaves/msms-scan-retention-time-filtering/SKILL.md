# MS/MS scan retention-time filtering

## Summary

Selects, for each feature–lipid candidate pair, the MS/MS scans from .ms2 files that fall within a user-defined retention-time and m/z tolerance of the feature, where the m/z tolerance equals the isolation window used for ion selection. This is Step 2 of the LipidMatch identification workflow and defines the fragment pool for subsequent ppm-level fragment matching.

## When to use

Use when processing ddMS2-topN or AIF UHPLC-HRMS/MS .ms2 files after MS1 exact-mass matching: you need to isolate the tandem-MS scans co-eluting with each feature before matching experimental fragments against in silico library m/z values.

## When NOT to use

- Input MS/MS data is still in vendor raw format — LipidMatch requires .ms2 files, so MSConvert peak picking and conversion must happen first
- Data comes from Waters files, which LipidMatch does not currently support
- You only have MS1 full-scan data with no ddMS2-topN or AIF spectra acquired from pooled/representative samples

## Inputs

- Feature table(s) per polarity type from MZmine, XCMS, or MS-DIAL (feature m/z and retention time)
- .ms2 files of MS/MS spectra generated by MSConvert peak picking/conversion
- Feature–lipid candidate pairs from LipidMatch MS1 exact-mass matching (user-defined m/z tolerance in Da)
- User-defined RT tolerance and m/z tolerance (set equal to the isolation window)

## Outputs

- Per feature–lipid pair, the subset of MS/MS scans within the RT and m/z tolerance window, passed to fragment matching
- Downstream per-lipid-class .csv fragment statistics tables (scan count, average m/z, maximum intensity, RT at max intensity, binary 0/1 flag)

## How to apply

Load the feature table (produced by MZmine, XCMS, or MS-DIAL) and the MSConvert-generated .ms2 files into LipidMatch (written in R with a gWidgets/tcltk dialogue-box UI). For each feature–lipid candidate pair from the MS1 exact-mass matching stage, retrieve MS/MS scans whose retention time lies within the user-defined RT tolerance and whose precursor m/z falls within the user-defined m/z tolerance, which should be set to the isolation window used for ion selection. Rationale: features can contain multiple co-eluting molecules with similar m/z values, so only scans within the feature's co-elution window should contribute fragments for that candidate. The selected scans then feed Step 3, where experimental fragments are matched against in silico lipid fragment m/z values within a ppm tolerance window. Iterative exclusion (IE) on pooled samples beforehand increases the number of ions with fragmentation spectra available for this selection.

## Evaluation signals

- Every selected MS/MS scan's precursor m/z lies within the user-defined tolerance, which should equal the isolation window used for ion selection
- Every selected scan's retention time falls within the user-defined RT tolerance of the feature's RT
- Features without any .ms2 scans in the window yield no fragment matches downstream (empty candidate statistics)
- Downstream .csv tables per lipid class exist and each binary 0/1 fragment flag is 1 only when the fragment was found within the ppm tolerance and met both intensity and scan-count thresholds
- Feature table gains appended LipidMatch identifications after the run, per the documented directory layout (Fig. 2)

## Limitations

- Scan availability depends on ddMS2-topN acquisition; iterative exclusion on pooled samples is recommended to increase ions with fragmentation spectra, so sparse acquisition limits this step
- LipidMatch was tested on Windows 7 through 10 and pinned to R 3.3.3; no cross-platform support is stated
- Waters files are not currently supported
